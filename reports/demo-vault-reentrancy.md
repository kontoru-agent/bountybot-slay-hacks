## Summary

`withdraw()` sends ETH to the caller via a low-level call and only zeroes the caller's share balance afterwards (checks-effects-interactions violation). A receiver contract re-enters `withdraw()` on every ETH receipt against the same un-updated balance and drains the vault.

## Impact (exact numbers, from the PoC)

- Vault balance before the attack: **100 ETH** (victim deposit).
- Attacker deposit: **1 ETH**.
- Attacker drained: **101 ETH** — its own 1 ETH plus the victim's entire 100 ETH.
- Vault balance after the attack: **0 ETH**.
- The victim's shares are untouched on paper but worthless: the vault is empty, so their claim redeems nothing.
- Preconditions: none. Any address can run this; no victim cooperation, no privileged role, no timing window.

4. The vault ends at 0 ETH; the attacker holds 101 ETH.

## Root cause

In `src/DemoVault.sol`, `withdraw()` performs the external call before the state update:

```solidity
(bool ok, ) = msg.sender.call{value: amount}("");
require(ok, "ETH transfer failed");
shares[msg.sender] = 0;   // <-- too late: the call above already ran
```

## Suggested fix

Follow checks-effects-interactions: update the state before the call, and add a reentrancy guard for defence in depth:

```solidity
shares[msg.sender] = 0;
totalShares -= amount;
(bool ok, ) = msg.sender.call{value: amount}("");
require(ok, "ETH transfer failed");
```
